# 《Metropolis: Roaring Times》Figma 地图交付与素材流程

> 文档用途：老板向 Codex 交付地图素材时必须遵守的权威合同
>
> 源文件作者：老板（使用 Figma）
>
> 接入负责人：老板交付后由 Codex 负责
>
> 玩家可见语言：英文；本开发文档：中文

## 一、权责与不可违反的边界

正式底图美术和分区几何都由老板在 Figma 中创作并批准。Codex 可以检查、转换、优化和接入老板提交的素材，但不得自行发明、重画、近似或暗中修正分区边界。

老板提供的 1939 年曼哈顿图片是锁定的视觉参考，不是正式底图，也不得被打包进游戏发布版本。

老板提交第七节规定的最低交付包，并且 Codex 完成素材接收报告之前，不得开始 M1A 地图实现。缺少素材属于必须向老板报告的依赖，不代表 Codex 获得制作占位地理的许可。

## 二、Figma 矢量画布与坐标

所有地图相关页面使用同一个主画框：

| 设置项 | 必须使用的值 |
|---|---|
| 画框名称 | 自定；推荐 `MAP_MASTER_VECTOR`，旧名 `MAP_MASTER_4474x5904` 仍兼容 |
| 宽度 | 不限，以老板实际矢量画布为准 |
| 高度 | 不限，以老板实际矢量画布为准 |
| 宽高比 | 不限，以老板批准的实际构图为准 |
| 方向 | 竖版，北向朝上 |
| 坐标原点 | 左上角 `(0, 0)` |
| 旋转 | `0°` |
| 主交付格式 | SVG 和完整结构 JSON |
| PNG | 可选 sRGB 预览；超大画布 PNG 失败不阻止交付 |

画布宽高只用于建立统一坐标，不限制游戏里的放大和缩小。镜头缩放只改变玩家看到的地图范围，不会改变分区位置。

同一版本中的底图、分区和对齐素材必须使用完全相同的实际画布、原点和边界。老板可以使用任意尺寸；但未经老板批准，不得只对其中一个图层裁切、缩放、旋转、增加外边距或移动内容。确需变更时，所有地图层必须同步迁移。

## 三、Figma 必备页面

按照以下固定顺序建立页面：

```text
00_README
01_REFERENCE
02_MAP_BASE
03_DISTRICT_GEOMETRY
04_ALIGNMENT_REVIEW
05_FUTURE_BUILDING_ANCHORS
```

页面名保持英文是为了稳定导出和程序识别，页面说明使用中文。

### `00_README`（项目说明）

应当写明：

- 项目名称和地图版本；
- 同一实际矢量画布和坐标注册要求；
- 北向朝上的要求；
- 第七节规定的导出文件名；
- 当前作者和日期；
- 修改记录；
- “建筑和游戏状态颜色不得画入底图”的警告。

### `01_REFERENCE`（历史参考）

- 将老板提供的历史参考图放在当前地图矢量画布内。
- 锁定参考图。
- 此页面不得产生任何正式游戏导出素材。
- 所有裁切或对齐辅助线必须锁定，并命名为 `registration_guide_do_not_export`。

### `02_MAP_BASE`（正式底图）

放置玩家实际看到的正式地图美术。使用第四节的图层结构，不得包含任何公共或私人建筑插画，也不得包含会随游戏变化的状态。

### `03_DISTRICT_GEOMETRY`（分区几何）

在相同的实际矢量画布中放置老板绘制的分区。每个分区都必须是可编辑、闭合的矢量形状，并使用第五节规定的稳定名称。

### `04_ALIGNMENT_REVIEW`（对齐审查）

仅用于审查：将正式底图、分区轮廓和英文分区名叠加在一起，供老板和 Codex 确认美术与几何位于同一位置。

### `05_FUTURE_BUILDING_ANCHORS`（未来建筑锚点）

留给以后经过批准的阶段。第一次地图交付时应保持为空，除非老板主动提交建筑锚点。Codex 不得因为页面为空就自行放置建筑。

## 四、老板批准的地图图层结构

在地图 Figma 源文件中，按照面板从上到下使用以下固定顺序。该顺序是老板根据实际遮挡结果批准的生产顺序，不得为了通用模板重新排序：

```text
06_FRAME
05_NON_BUILDING_ORNAMENT
04_ROADS
03_DISTRICT_GEOMETRY
02_COASTLINE
01_WATER
```

图层名保持英文是为了稳定导出和程序识别。具体规则如下：

- 六个地图顶层图层在 Figma 源文件中保持独立可编辑。
- `06_FRAME`、`05_NON_BUILDING_ORNAMENT`、`04_ROADS`、`02_COASTLINE` 和 `01_WATER` 可以合并到正式底图 SVG 或可选 PNG 预览，但不得在 Figma 主文件中永久合并。
- `03_DISTRICT_GEOMETRY` 只用于权威分区几何和对齐审查，导出正式底图时必须隐藏。
- `00_BRAND` 是独立 Logo 素材，可以保留为 Figma 同级图层，也可以像当前项目一样单独交付；不得烘焙进正式底图。其正式标题必须为 `Metropolis: Roaring Times`，并保留老板批准的公开署名 `designed and drawn by GatChive`。
- 所有底图图层都不得包含公共或私人建筑插画。
- 市政厅、公共图书馆等建筑即使属于政府，也要在后续作为独立建筑素材交付。
- 所有权、悬停、选择、地块边界、繁荣度、法律警告和施工状态不得画入底图。
- 玩家看到的地图颜色遵守 `04_MAP_AND_ART_DIRECTION.md`；分区识别用的技术色不是游戏配色的一部分。

## 五、`03_DISTRICT_GEOMETRY` 图层结构

在同一个实际矢量画布内使用以下结构：

```text
03_DISTRICT_GEOMETRY
├── district_inwood
├── district_washington_heights
├── district_harlem
├── district_upper_east
├── district_upper_west
├── district_midtown_west
├── district_midtown_east
├── district_chelsea
├── district_west_village
├── district_east_village
├── district_soho
└── district_financial_district
```

上述 12 个节点是首版唯一权威分区集合，旧六分区/五玩法区结构不再有效。每一项都必须：

- 由老板绘制并批准；
- 是闭合矢量形状，或由多个闭合形状组成并使用统一名称的组；
- 在正式 SVG 中保留稳定 `id` 和可提取矢量路径；
- 不使用图片作为分区边界；审查用填充、描边或效果可以存在，但运行时转换必须忽略它们，只读取权威路径；
- 完整位于主画框之内；
- 不与其他分区意外重叠；如有意重叠，必须由老板在说明文件中记录；
- 保持上述稳定图层名完全不变。

Central Park 是公共非分区空洞；河对岸陆地是首版非交互背景。12 区的经济画像尚未批准，不得从旧五玩法区自动继承。

## 六、分区审查样式

分区节点可以使用统一紫色或其他老板批准的临时审查样式；程序依靠稳定 `id` 区分分区，不依靠技术颜色。分区 SVG 是边界几何的唯一权威。填充、描边、阴影和滤镜只用于人工审查，运行时几何转换必须忽略这些表现属性，也不能以它们为理由重画边界。

## 七、一键交付文件包

为避免老板反复隐藏图层、分别导出和手工确认坐标，正式流程优先使用项目内的本地 Figma 插件：

```text
tools/figma_handoff_exporter/
```

老板在 Figma 桌面版选中地图主画框；如果六个规定地图顶层图层没有被外层 Frame 包裹，则选中其中任意一层即可。运行 `Metropolis Handoff Exporter` 并点击“一键导出 ZIP”。插件按实际矢量画布建立不写回原稿的虚拟主画框，并生成完整/底图 SVG、分区 SVG、对齐 SVG、成功的逐层 SVG、原始图片和完整结构 JSON；PNG 仅作尽力导出的便利预览。老板不再需要手工完成多次导出。详细安装说明见该目录 `README.md`。

插件 ZIP 保存网页接入需要的图层关系、位置、颜色、矢量和图片，但不能保存 Figma 版本历史、评论和协作信息，因此老板仍需另行保存一个 `.fig` 本地副本。

### 归档目录

老板提交一个带版本号的文件夹：

```text
metropolis_map_vNNN/
├── source/
│   └── metropolis_roaring_times_map_vNNN.fig
├── handoff/
│   └── metropolis_handoff_<timestamp>.zip
└── OWNER_NOTES.md
```

归档必须包含：

1. **Figma 源文件（`.fig`）**：可编辑的权威源文件和版本快照。
2. **插件 ZIP**：内含完整地图 SVG、底图 SVG、分区 SVG、对齐 SVG、完整图层树 JSON、成功导出的逐层 SVG、原始图片和可选 PNG 预览。
3. **老板说明 `OWNER_NOTES.md`**：记录版本、作者、交付日期、已知未完成区域和任何有意进行的地理变形。

ZIP 不限制固定像素尺寸。底图 SVG 不得包含参考图层、分区交互层、Brand、建筑或游戏状态；分区 SVG 必须使用与结构 JSON 记录的实际画布一致的 `viewBox`。对齐 SVG 用于人工审查。PNG 是可选预览，超大画布无法导出 PNG 不构成交付失败。Brand 必须独立、透明，并符合第四节标题和署名要求，但可以作为项目中的单独文件交付。

即使老板提供了在线 Figma 链接，在该素材包成为正式项目依赖前，仍必须提供 `.fig` 快照。

## 八、底图与分区为什么能够准确对位

底图 SVG、分区 SVG 和对齐 SVG 使用相同画布、`viewBox` 和原点。因此，这些文件中的 `(x, y)` 都代表地图上的同一个位置。

接入游戏时，Codex 将老板提交的 SVG 坐标换算为归一化地图坐标：

```text
normalized_x = svg_x / actual_canvas_width
normalized_y = svg_y / actual_canvas_height
```

游戏中的放大、缩小和拖拽只会改变镜头，不会改变这些归一化位置。只有新底图继续使用已经批准的裁切范围和宽高比，替换底图才不会导致分区错位。

## 九、Codex 接收素材后的固定流程

老板提交 `.fig` 与插件 ZIP 后，Codex 必须依次执行：

1. 将提交包原样保存在 `references/incoming/`，不修改源文件。
2. 记录文件名、尺寸、校验值、源文件作者和日期。
3. 检查插件结构 JSON 与所有生产导出，读取实际画布宽高，确认所有 SVG 使用完全一致的 `viewBox` 和原点；不按固定像素尺寸判退。
4. 将分区 SVG 与插件生成的对齐预览叠加到底图上，制作对齐报告。
5. 检查未闭合路径、意外重叠、空隙、重名、缺名和超出画框的几何。
6. 将对齐预览与权威源文件比较，不得自行修正地理。
7. 把每一项缺陷或歧义报告给老板。
8. 等待老板提交修正版，或者明确接受某项有意差异。
9. 将批准后的 SVG 转为归一化运行时 JSON，不改变任何顶点。
10. 把派生文件加入 `assets/` 或 `data/`，记录来源，并测试源文件没有进入游戏发布包。
11. 先向老板展示 M1W 网页对齐结果；M1W 验收并另获授权后，才进入 Godot M1A，且仍须在制作 64 个地块前展示 Godot 对齐结果。

未经老板看到修改前后对比并明确批准，禁止自动简化、平滑或删除顶点。

## 十、建筑与缩放层级的边界

- 第一次地图交付的底图中不包含任何独立建筑插画。
- 公共建筑和私人建筑以后作为独立透明素材交付。
- 两类建筑使用同一个由老板批准的近景显示阈值。
- 远景和中景的分区摘要、建筑数量和繁荣度由程序界面生成。
- Codex 后续可以提出建筑锚点方案，但批量放置前必须由老板批准。

## 十一、必须拒收并停止的情况

出现以下任意情况时，Codex 必须停止接入并向老板报告阻塞问题：

- 缺少任何必备文件；
- 尺寸、裁切、方向或 SVG 画框不一致；
- 分区图层名称缺失或被修改；
- 分区形状未闭合、意外重叠或超出画框；
- 底图中已经画入公共/私人建筑或游戏状态；
- 正式底图导出中出现历史参考图；
- Codex 无法证明底图、SVG 和蒙版使用同一套坐标登记。

被拒收的文件仍然保持原样保存，绝不暗中覆盖。
